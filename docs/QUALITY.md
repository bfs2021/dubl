# Качество и скорость движка «Дубль» на настоящих фильмах

Замеры на Mac17,3 (Apple M5, 16 ГБ, macOS 26), ffmpeg 9.0.2, Python 3.11, torch 2.5.1, faster-whisper 1.2.1, mlx-whisper 0.4.3.
Материал — Blender Open Movies (`samples/README.md`): **Tears of Steel** (12:14, 5.1 + эталон «музыка и шумы без диалога» + SRT en/ru),
Sintel (14:48, MKV-релиз с 10 дорожками субтитров), Elephants Dream (в замерах почти не участвует).

> **Оговорка о нагрузке.** Все замеры шли на рабочем компьютере, на котором параллельно работали другие агенты (load average 3–9,
> иногда выше), поэтому **время завышено** — на чистой машине будет быстрее, возможно заметно (особенно CPU-часть: faster-whisper).
> Память (пик) от нагрузки почти не зависит. Шаги запускались строго по одному. Все цифры — один прогон, без усреднения;
> разброс между повторами 5–15 % (повторяли e2e и separate), для «медленных» шагов — больше.
>
> **Как воспроизвести:** `python3 samples/fetch.py`, затем `cd engine && tests/e2e/rb.sh <имя> <шаг> [арг]`
> (шаги — функции `step_*` в `engine/tests/e2e/bench.py`; пик памяти берётся из `/usr/bin/time -l`:
> `peak_rss_mb` — «maximum resident set size», `peak_footprint_mb` — «peak memory footprint», **он включает память GPU/MPS**;
> RSS её не видит, поэтому для нейросетей на Apple GPU верить надо footprint). Сырые JSON — в `samples/work/bench/`.
> Тесты: `cd engine && .venv/bin/pytest -m slow tests/e2e` (34 теста, ≈ 6 мин, пик 3,5 ГБ RSS / 9,3 ГБ footprint — из-за BS-RoFormer; см. «Память продукта»).

Доля реплик SRT, лежащих внутри речи по Silero VAD (микс): порог 0,5 — среднее покрытие 0,50 (36 реплик покрыты < 50 %), 0,2 — 0,62, 0,03 — 0,86, 0,01 — 0,89; на центре 0,76 / 0,84 / 0,94 / 0,98.
Silero на фильмах отдаёт вероятности речи 0,00–0,25 для диалога под оркестром, поэтому пороги штатной шкалы (0,3–0,5) бесполезны, а «мягкий» VAD режет лишь настоящую тишину.

**Про «744 секунды».** Это суммарное время прогона `whispervar` — **шести** вариантов подряд (38+60+232+55+85+272 с), а не одного.
Одиночные прогоны turbo на faster-whisper: 29–55 с с VAD и ≈221 с без VAD (0,30×RT) — под нагрузкой от других агентов.
Но вывод пользователя верен по сути: без VAD CPU-путь медленный, а с VAD (как в движке) — быстрый, но теряет диалог.

Что видно:

1. **VAD в `transcribe()` — главная проблема точности.** `vad_filter=True` с настройками по умолчанию режет речь поверх музыки:
   на миксе из 76 реплик находится 41, WER 0,42. Без VAD — 68 реплик, WER 0,27 (но в 8 раз дольше и появляются галлюцинации
   «Thank you.» на музыке в конце). С центральным каналом VAD почти не мешает (WER 0,18).
2. **mlx-whisper даёт лучшее соотношение:** без VAD, WER 0,235 на миксе / 0,193 на центре за 34–40 с. Он быстрее faster-whisper
   без VAD в 5,5–6,6 раза. По точности на миксе — как faster-whisper без VAD (0,27) или лучше.
3. **Центр 5.1 как вход whisper** улучшает WER у всех, кроме mlx-small (там хуже: 0,36 против 0,32 — малая модель с центром путается на SFX-хвостах).
   Для turbo выигрыш: faster 0,42→0,18, mlx 0,235→0,193.
4. **Тайминги слов.** Медиана сдвига первого слова −0,05…−0,14 с (whisper ставит слово чуть раньше эталона; эталон SRT округлён до 0,5 с, поэтому
   разброс «среднее по модулю» 0,4–0,9 с частично принадлежит самому SRT). У mlx и faster без VAD среднее по модулю одинаковое (0,41–0,47 с),
   у faster с VAD — 0,9–1,6 с (потерянные реплики).
5. small против turbo: на этом материале turbo лучше только на mlx/центре (0,193 против 0,361). На faster-whisper с VAD small и turbo равны (0,42).
   small быстрее в 2 раза. Для 90-минутного фильма разница — минуты.
6. **Галлюцинации.** mlx без VAD вставляет «Thank you.»/«I'm sorry.»/«We'll be right back.» на музыке и в титрах, а в тихом месте 263–287 с
   «зацикливается» на «I'm going to go to the next video.» ×15. Штатные пороги whisper (`no_speech_prob`, `logprob`) эти фразы **не ловят**:
   `no_speech_prob` = 0,00 у всех, `avg_logprob` −0,3…−1,0 (и у настоящих реплик тоже). Работает только сумма признаков
   (`transcribe.hallucination_score`, порог 3): средняя вероятность слов (< 0,4 → +2, < 0,6 → +1), `avg_logprob`, зацикливание (одна фраза ≥ 3 раза за 90 с),
   «фразы из YouTube» («next video», «be right back», «subscribe»…), одинокая реплика (> 4 с до соседей), слова, растянутые на секунды, и энергия звука
   в этом месте (тише «громкого места» файла на 25 дБ — +1,5, на 40 — +4). Одно слово с низкой уверенностью в разгар диалога не отбрасывается.

### Распознавание русской речи: GigaAM v3 + язык по речи

**Что сделано.** (1) Язык оригинала при «Определить по речи» берётся из речи: Whisper `detect_language` на 2–3 окнах по 30 с,
где больше всего громких мест, вероятности складываются (`transcribe.choose_language`); метка дорожки — только подсказка, если речь
неразборчива (средняя вероятность < 0,6). Выбор человека — закон. Расхождение с меткой сохраняется в `Analysis.language_note`
и показывается в разборе. (2) Настройка `asr_engine` = auto | whisper | gigaam: auto — русская речь → **GigaAM v3 e2e-rnnt**
(Сбер, MIT; ONNX int8 через `onnx-asr`, CPU), остальное → Whisper. (3) **Добор Whisper'ом**: реплики GigaAM со средней
уверенностью слов < 0,8 (≈ 1/3 реплик) переслушиваются Whisper'ом (окно ±8 с, язык ru, фильтр выдумок приложения); текст
заменяется, если Whisper увереннее хотя бы на 0,05 (и ≥ 0,6), услышал новое, это кириллица и не пометка/титр. Границы реплик
остаются от GigaAM (начало сдвигается к Whisper'у, только если он услышал начало, которого у GigaAM нет: «гард!» → «Ангард!»).

**Почему GigaAM для русского.** Whisper ставит начало реплики систематически на 250–350 мс раньше голоса — для замены голоса это
главная ошибка. GigaAM в 3 раза точнее по границам, без выдумок, с пунктуацией, но сам по себе теряет короткие выкрики
(«Ангард!», «Тайм-аут!» → «Дай боу!»). Добор возвращает их и вдобавок правит сомнительные слова — итог лучше обоих по тексту.
На английском GigaAM пишет транслит-мусор, поэтому только после определения языка. Почему ONNX, а не пакет `gigaam`: v3 есть
только на GitHub, тянет torch/hydra; onnx-asr даёт тот же текст и границы (±1 мс) на всех ОС; CoreML-провайдер onnxruntime
на энкодере GigaAM падает — провайдер всегда CPU. Int8-сборка по тексту не хуже fp32 (WER 0,136 против 0,148, границы те же),
а качать 216 МБ вместо 892 МБ.

#### Что сделано в `diarize.py`
1. **Число голосов — по силуэту, а не по порогу.** Порог 0,98, подобранный на одном фильме, давал на Sintel и Cosmos 3 голоса (один человек делился на 2–3). Теперь строим дерево (average linkage по косинусу, эмбеддинги ECAPA после вычитания среднего по фильму), режем на k = 2…kmax групп, мелкие (`min_cluster_size`) присоединяем, берём k с лучшим средним силуэтом; при равенстве — меньшее. Если лучший силуэт < 0,08 (шум в 192 измерениях даёт ≤ 0,055, настоящие фильмы ≥ 0,11) — голос один.
   `kmax = max(6, n/9)`, не больше 16: без верхней границы силуэт дробит длинный фильм по сценам (одинаковый голос в разных обстановках). На kmax 7–9 ToS одинаково хорош; Sintel и Cosmos от kmax 4…10 не зависят.
2. **Перекрытие по времени.** Реплики, пересекающиеся > 0,3 с, считаются разными людьми: их расстояние = 2 (макс.), а после разбиения `enforce_no_overlap` выносит одну из пары в другую группу. На ToS/Sintel/Cosmos с whisper-выравниванием таких пар нет, так что метрики не меняет; защита от склейки двух одновременных голосов при плохом выравнивании.
3. **Детерминизм.** Расстояния округляются до 1e-6 (шум float32 от числа потоков не может переставить слияния), ничьи решаются по минимальному k / индексу, `diarize` сортирует реплики по `(start, end, id)`, предложения — по `(-sim, a, b)`. Случайности нет (ни KMeans, ни семплирования). Тест на трёх фильмах: потоки torch 1 / 4 / по умолчанию × прямой, обратный и случайный порядок реплик → идентичные `speaker_id`, `line_count`, `total_speech`, `merge_suggestions`.
4. **`merge_suggestions`.** Предлагаем пару только если центроиды взаимно ближайшие и (1 + косинус) / 2 ≥ 0,55 (раньше — любая выше порога). На разметке принудительно мельче нарезанных фильмов (порог 0,85/0,9/0,95 × 3 фильма × микс/центр) верное первое предложение (оба кластера — один персонаж): **15 из 16**; в целом топ-3: 29 из 30 при «взаимности» против 35 из 37 без неё (практически то же, но втрое меньше шума). Старое правило на ToS предлагало слить Селию с помощницей (0,53), новое в обычном режиме — ничего.
   В обычном режиме предложений нет: силуэт выбирает разбиение, где кластеры достаточно далеки (центроиды: косинус −0,02…−0,5), и «похожих» пар не остаётся.

### Как встроен mlx-whisper (сделано в `analysis/transcribe.py`)

1. **Зависимость.** `pip install mlx-whisper` (в `engine/.venv` версия 0.4.3; тянет `mlx`, `mlx-metal`). В `pyproject.toml` — extra `mlx` с маркером
   `sys_platform == 'darwin' and platform_machine == 'arm64'`; `packaging/ml_pack.py` на Mac arm64 ставит `dubl_engine[ml,mlx]`, на остальных `[ml]`.
2. **Выбор бэкенда** — `pick_backend(model, device)`: `"mlx"`, если Mac arm64, `import mlx_whisper` удался, модель из `MLX_REPOS` (tiny/base/small/medium/large-v3/large-v3-turbo)
   и `device != "cpu"`; иначе `"faster"` (CUDA float16 или CPU int8). Если mlx упал во время работы — тихо переходим на faster-whisper. Сигнатура: `transcribe(path, language=, model=, on_progress=, device=, backend=None, vad=None)`.
3. **Нарезка.** mlx-whisper не имеет прогресса, поэтому звук режется на куски ≈ 5 мин по самому тихому месту (±20 с вокруг границы) — отсюда `on_progress` и ограничение памяти. Слова с таймингами (`word_timestamps`) → те же `split_words`/`_segment_to_groups` (резка > 8 с по паузам > 0,6 с).
4. **Модели** — `data_dir()/models/mlx/<repo>` (скачиваются `snapshot_download(local_dir=…)`); если не вышло — общий HF-кэш. turbo — 1,6 ГБ.
5. **Фильтр галлюцинаций** — `drop_hallucinations` для обоих бэкендов (см. пункт 6 выше). Штатные пороги mlx отключены (`no_speech_threshold=None`, `logprob_threshold=None`, `compression_ratio_threshold=None`): они отбрасывали вместе с мусором и реальные реплики.
6. **Память.** turbo ≈ 3,7–3,9 ГБ footprint — не запускать вместе с `best`-разделением (9 ГБ). После `transcribe()` вызывается `release_memory()` (gc, `mx.clear_cache()`, `torch.mps.empty_cache()`), диаризация освобождает ECAPA.

### 1. `align_embedded_to_speech` схлопывает соседние реплики в один интервал — **исправлено**
Было: только вход из SRT без перекрытий, whisper turbo на миксе. 16 из 76 реплик сдвигались больше чем на 0,8 с (максимум 4,8 с), у 12 пар соседей после выравнивания интервалы
перекрывались, l0038/l0039 получали один интервал 316,16–323,63 (сдвиг −4,84 с), l0055 «взято от l0057». Причина — `_align_one` брал максимум перекрытия отдельно для каждой строки и не запрещал группам пересекаться.
```python
en = parse_subtitle_file("samples/raw/TOS-en.srt"); w = [Line(**d) for d in json.load(open("samples/work/analysis/whisper_large-v3-turbo.json"))]
al = align_embedded_to_speech(en, w)
```
Стало (`analysis/align.py` переписан): слова SRT и слова речи сопоставляются **одним монотонным проходом** (динамическое программирование, как diff: каждое слово речи достаётся максимум одной
строке; штраф за расстояние по времени), границы строки — по первому/последнему совпавшему слову (недостающие края достраиваются по 0,32 с на слово), «чужие» слова на краю (пауза > 0,7 с) отбрасываются,
слова whisper, растянутые на паузу, укорачиваются до разумной длины. Затем `_resolve`: никаких новых перекрытий (перекрытие SRT допустимо только исходное), порядок сохранён, длина не больше `2 × исходная + 1 с`, сдвиг
≤ 3 с при совпадении ≥ 90 % текста, ≤ 1,5 с при ≥ 75 %, ≤ 0,8 с иначе и при выравнивании только по времени; нет уверенности (< 50 % слов, одно слово из многих, укороченный в 2,5 раза интервал) — тайминг SRT.
